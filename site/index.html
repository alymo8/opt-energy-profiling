Energy and Resource Profiling of OPT-350m Training

Where does the energy go when you train a language model? We measured time, energy and GPU use for every training step of OPT-350m at three batch sizes, and found that one phase, the optimizer step, keeps the GPU from staying busy.

Aly Mohamed · April 2026

Research questions

We built a controlled measurement framework around Meta's OPT-350m to answer three questions.

Instrumentation cost

How much overhead does detailed, per-step energy and resource measurement add to training?

Batch size vs. efficiency

How does batch size affect throughput, energy per step and energy efficiency?

Lost GPU capacity

Where inside the training loop does GPU utilization fall short of its maximum, and why?

Experimental setup

facebook/opt-350m in FP32 with sequence length 1024, learning rate 1e-6, seed 1234 and synthetic token data, so data loading adds no I/O. Every step is split into forward, backward and AdamW update, with torch.cuda.synchronize() around each phase so the timings reflect GPU work, not kernel dispatch. Batch sizes were picked by probing the largest size that fits in memory, which was 16, then halving it twice.

ForwardBackwardOptimizer (AdamW)

The optimizer doesn't scale with batch size. AdamW updates all 350M parameters on every step, however much data that step processed, so it holds at about 96 ms. It launches many small, memory-bound CUDA kernels that don't fill the GPU. At batch 4 it takes 39% of each step, and average utilization drops to 83%.

Where to gain efficiency

The measurements point to four concrete next steps.

Fused optimizer kernels

Merging AdamW's per-tensor kernels into a single fused kernel attacks the fixed 96 ms directly. That would recover most of the lost utilization at small batch sizes.

Gradient checkpointing

Batch 16 was limited by memory, not compute, and efficiency was still rising. Trading recompute for memory would make larger, more efficient batches fit.

Use the idle capacity

On a shared cluster, the optimizer's unused GPU capacity can be given to another workload. A scheduler could co-locate light inference or preprocessing jobs instead of pushing one job to 100%.

Dedicated node

Shared-cluster noise was small (under 0.6 s spread across repeats). Smaller gains, such as those from kernel fusion, would need an isolated node to measure.

Reproduce it

The repository contains the training framework, the experiment runner, the aggregation and plotting scripts, and all raw logs from the final run.

git clone https://github.com/alymo8/opt-energy-profiling
cd opt-energy-profiling
pip install -r requirements.txt

# batch sweep x profiles A/B/C x 3 repeats of 300 s
python3 scripts/run_opt_experiments.py --repo-root . \
  --output-root ./results/e2e_experiments/run-N \
  --launcher "python3 launch.py" --duration-sec 300 --repeats 3

python3 scripts/aggregate_opt_experiments.py ./results/e2e_experiments/run-N/<opt-run-timestamp>
